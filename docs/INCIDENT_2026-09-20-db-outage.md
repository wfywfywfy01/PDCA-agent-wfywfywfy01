# 事故复盘：2026-09-20 生产数据库主机冻结

## 现象

- 工作台所有依赖数据库的接口返回 **500**，`/health` 返回 **503**（降级）。
- 静态页面仍可打开（77ms），说明应用进程本身存活。
- 当天日志出现 **1693 次** `OperationalError ... timeout expired`，此前数天为 **0**。

## 根因（已更正）

**本机 VPN（OpenVPN Connect → `vpn-cd.vertu.cn`）断开**，导致内网数据库 `10.100.0.176` 不可达。

| 探测 | 结果 | 说明 |
|------|------|------|
| OpenVPN Connect DCO Adapter | **Disconnected** | VPN 数据通道未建立（TAP 网卡残留手动 IP 172.123.178.233 仍为 Up，具有迷惑性） |
| TCP 22/80/443/5432/2375 | 可建立连接（52–62ms） | **企业网络设备在本地完成握手**，并不代表对端服务可用 |
| SSH banner / HTTP / Docker API / PostgreSQL 握手 | 全部无响应 | 与“TCP 可连”组合在一起，是“路径被黑洞”的特征，而非主机存活 |
| 随机高端口 | 超时 | 排除“所有端口假开放” |

> **更正说明**：首次判断为“数据库主机 10.100.0.176 应用层冻结”并建议重启该主机。
> 用户重启后症状完全不变，且本机 VPN 网卡处于断开状态——真正原因是**本机到内网的 VPN 通路中断**。
> 请以本节为准；“TCP 可连但协议无响应”在 VPN 断开场景下会稳定复现，不能作为主机故障的证据。

## 为什么第一次判断会出错（经验）

1. 企业网络对放行端口会**本地完成 TCP 三次握手**，于是“端口是通的”这个直觉完全不可靠；
2. VPN 断开时残留 TAP 网卡仍显示 Up 并持有手动 IP，容易被误读为“内网可达”；
3. 正确顺序应当是：**先看 VPN 网卡 → 再做协议层探测 → 最后才怀疑对端主机**。
   守护脚本 `scripts/db_guard.ps1` 已按此顺序实现，告警会直接给出“先恢复 VPN”的结论。

## 放大因素（真正的可预防点）

1. **备份长期失败，导致没有恢复点**：
   远端库是 PostgreSQL **18.4**，本机 pg_dump 只有 **16.9 / 12.18**，
   每天 06:00 的 `backup_database()` 直接报 `aborting because of server version mismatch`，
   `pdca-workbench/data/backups/` 为空（最近一份还是 6 月）。
2. **故障发现依赖工作台自身调度**：17:15 开始故障，17:30 才由定时任务触发告警；
   若工作台进程本身挂掉，就完全没人报信。
3. **UI 静默降级**：接口 500 时导航里的用户区与管理入口无声消失，用户不知道发生了什么（已修复）。

## 已实施的防护

| 措施 | 落点 | 说明 |
|------|------|------|
| 数据库守护 | `scripts/db_guard.ps1` + 计划任务 `PDCA-DBGuard`（每 5 分钟） | 协议层探测（避免“端口开着但服务卡死”误判）；故障/恢复**状态变化时**推送 IM 告警；数据库恢复而工作台未起来时**自动拉起并复验** |
| 版本无关逻辑备份 | `scripts/pg_logical_backup.py` + 计划任务 `PDCA-LogicalBackup`（每日 06:30） | 用 psycopg2 逐表导出 gzip JSONL，**不依赖 pg_dump 版本**，规避 18.4 vs 16.9 不匹配；保留最近 14 份 |
